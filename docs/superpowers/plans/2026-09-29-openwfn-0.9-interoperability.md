# openWFN 0.9 Interoperability Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add stable, capability-aware ingestion for the complete IOData 1.0.1 readable input-format surface while preserving openWFN's existing FCHK workflows and scientific result contracts.

**Architecture:** Keep native openWFN parsers authoritative where they are already validated, especially Gaussian FCHK. Add an optional IOData adapter behind an openWFN-owned `OpenWFNData` canonical container, then route Python API, CLI, batch, and analysis dispatch through one capability engine that decides what each normalized input can safely do.

**Tech Stack:** Python 3.10-3.13, dataclasses, NumPy, existing openWFN parser/analysis/result infrastructure, optional `qc-iodata==1.0.1` backend, pytest, Ruff, GitHub Actions, MkDocs.

**Spec:** `docs/superpowers/specs/2026-09-29-openwfn-0.9-interoperability-design.md`

## Global Constraints

- Preserve current Gaussian FCHK behavior and result meaning unless a separately justified scientific bug fix requires a change.
- Keep the core install independent of IOData; `pip install openwfn` must continue to work without the interoperability backend.
- Add the interoperability backend only through `pip install "openwfn[interop]"`.
- Pin the 0.9 interoperability contract to distribution `qc-iodata==1.0.1`; the Python import remains `iodata`.
- Treat the IOData 1.0.1 readable input-format snapshot as 25 format IDs: `charmm`, `chgcar`, `cp2klog`, `cube`, `extxyz`, `fcidump`, `fchk`, `gamess`, `gaussianinput`, `gaussianlog`, `gromacs`, `json_qcschema`, `locpot`, `mol2`, `molden`, `molekel`, `mwfn`, `orcalog`, `pdb`, `poscar`, `qchemlog`, `sdf`, `wfn`, `wfx`, `xyz`.
- Raw IOData objects must never appear in public openWFN Python return types, result records, CLI contracts, or batch manifests.
- A format is Stable only when its fixture-backed format contract passes; backend readability alone is not enough.
- Filename suffixes may choose a parser candidate but must never decide scientific capabilities.
- Expected scientific unavailability must return a structured openWFN result/error rather than an unexplained exception.
- Existing `RESULT_SCHEMA_VERSION == "1.0"` remains unchanged unless implementation proves a schema break is unavoidable; capability unavailability should use the existing failed-result envelope with `validation_status="Unsupported"`.
- 0.9 does not add QTAIM, new ML models, a plugin framework, an LLM feature, or unrelated scientific analysis families.
- Do not vendor IOData code or fixtures. Update `THIRD_PARTY_NOTICES.md` to identify the optional GPL-3.0-or-later backend and its version; keep the dependency optional and separately installed.

## Review Focus

- Ambiguous output names such as `*.out`: Gaussian output must remain readable, while ORCA/CP2K inputs must route to the correct backend and record the exact detected source format.
- Partial or malformed external outputs: if the backend returns an object missing fields normally associated with that format, openWFN must compute capabilities from actual normalized data rather than the format label.
- Periodic/grid/integral inputs: isolated-molecule analyses must remain unavailable unless their actual requirements are satisfied; no fake `CalculationData` may be constructed.
- Multi-record-capable formats such as XYZ/PDB/GROMACS: 0.9's public `load()` contract is single-input/single-record; extra records must never be silently merged into one structure.
- Missing optional backend inside both the main process and process-pool batch workers: error text must name `openwfn[interop]` rather than exposing a raw `ImportError`.
