# openWFN 0.11 Native Hirshfeld Design

Date: 2026-10-02
Status: Design proposal
Baseline: openWFN 0.10.1
Target: openWFN 0.11.x

## 1. Purpose

openWFN 0.11 will add a native Hirshfeld stockholder population/charge analysis as the next scientific expansion after the validated everyday-QC capabilities in 0.10.1.

The implementation must preserve openWFN's existing principles:

- scientifically conservative results;
- explicit validation status;
- reproducible numerical controls;
- provenance-aware outputs;
- capability-aware failure behavior;
- stable CLI/Python/batch/report/MCP contracts where scientifically appropriate;
- no promotion from Experimental to Validated without independent evidence.

The goal is not merely to print Hirshfeld charges. The goal is to provide a scientifically traceable stockholder analysis with documented reference densities, numerical convergence diagnostics, closure checks, explicit unsupported cases, and reproducible evidence.

## 2. Scope

### 2.1 Included in 0.11

1. Native Hirshfeld atomic electron populations and net atomic charges.
2. A versioned neutral-free-atom reference-density data package for supported elements.
3. Deterministic atom-centered molecular integration.
4. Charge and partition closure diagnostics.
5. Explicit treatment of restricted and unrestricted molecular densities through the total molecular density.
6. CLI, Python API, structured JSON, CSV export, reports, and batch support.
7. Read-only MCP exposure only after parity and bounded-runtime tests pass.
8. Validation against independent reference calculations for a documented molecular corpus.
9. Convergence tests for radial/angular quadrature and finite spatial support.
10. Clear rejection of unsupported ECP/reference-density cases.
11. Documentation, provenance fields, resource limits, tests, and release evidence.

### 2.2 Explicitly not included

The following are outside this unit and must not be silently folded into 0.11:

- Hirshfeld-I / iterative Hirshfeld;
- CM5 corrections;
- ISA/MBIS/DDEC or other stockholder variants;
- QTAIM charges;
- ECP pseudo-density reconstruction unless a separately validated design is approved;
- excited-state Hirshfeld charges;
- correlated-density reconstruction from insufficient source files;
- spectroscopy, NTO, QTAIM, ELF/LOL, NCI, or basin integration.

These remain future gated projects.

## 3. Scientific definition

For a molecular electron density rho(r) and neutral spherical free-atom reference densities rho_A^0(r), define the promolecular density

rho_pro(r) = sum_B rho_B^0(|r-R_B|)

and the Hirshfeld stockholder weight

w_A(r) = rho_A^0(|r-R_A|) / rho_pro(r).

The atomic electron population is

N_A = integral w_A(r) rho(r) dr

and the net atomic charge is

q_A = Z_A,eff - N_A.

For all-electron calculations, Z_A,eff is the nuclear charge. For any case involving an ECP, openWFN must use explicit source effective charges only if the corresponding reference-density convention is scientifically defined and validated. Otherwise the analysis is rejected rather than guessed.

The implementation must not renormalize final charges merely to force exact molecular charge closure. Numerical residuals are reported as diagnostics.

## 4. Reference free-atom densities

### 4.1 Requirements

Every supported element must have a neutral spherical reference density with:

- element and atomic number;
- source method;
- basis-set or numerical-atom method;
- software/version used to generate it;
- units;
- radial grid definition;
- normalization/electron-count check;
- generation date;
- content hash;
- redistribution/license status;
- provenance record checked into the repository or packaged data.

A hydrogenic approximation reused across elements is prohibited.

### 4.2 Preferred strategy

Generate a redistribution-safe first-party reference library from reproducible neutral-atom calculations using an openly available computational path and record the exact generation script and environment. The resulting radial densities are treated as versioned scientific data, not opaque constants.

The initial supported periodic-table range should be limited to the elements for which reference generation, normalization, and independent molecular validation are complete. Unsupported elements fail cleanly with a capability error.

### 4.3 Interpolation

Reference densities are stored on radial grids and interpolated using a documented monotone/nonnegative scheme. Interpolation must preserve non-negativity and avoid oscillatory negative tails.

Values outside the tabulated range are handled with an explicitly documented tail policy. The policy must be validated against expanded reference grids and may not silently truncate material density.

## 5. Molecular density source

Hirshfeld analysis consumes the same normalized molecular density machinery already used by openWFN density/ESP analyses.

Priority:

1. source-provided total AO density when trustworthy and applicable;
2. reconstructed total AO density from occupied orbitals only when the existing model contract permits it and provenance records the reconstruction;
3. reject inputs that lack a scientifically adequate total density.

For unrestricted calculations, alpha + beta total density is used for ordinary Hirshfeld charges. No spin-Hirshfeld quantity is implied unless separately specified in a later design.

Post-HF inputs must continue to disclose when only an SCF density is available. Hirshfeld must not imply use of a correlated density that is absent from the source.

## 6. Numerical integration

### 6.1 Atom-centered quadrature

Use atom-centered radial x angular quadrature with molecular partitioning appropriate for integrating the stockholder-weighted molecular density. The implementation must be deterministic and chunked to bound memory.

Numerical controls include:

- radial order/grid size;
- angular order/grid size;
- molecular partition/pruning policy;
- density screening threshold;
- radial extent/tail threshold;
- chunk size.

Defaults must be conservative, deterministic, and documented.

### 6.2 Convergence

A result can be scientifically successful only if required convergence/closure gates pass.

At minimum report:

- integrated molecular electron count;
- expected electron count;
- electron-count residual;
- sum of atomic Hirshfeld populations;
- population partition residual;
- sum of atomic charges;
- expected molecular charge;
- charge closure residual;
- promolecular near-zero handling count;
- quadrature settings;
- spatial/tail diagnostics;
- reference-density library version/hash.

The validation suite must include systematic grid refinement. A coarse-grid result that fails tolerance returns partial/Experimental status with warnings rather than being promoted by normalization.

## 7. Near-zero promolecular density

At points where rho_pro approaches numerical zero, the implementation must avoid unstable division.

Required behavior:

- if both molecular and promolecular densities are below documented negligible-density thresholds, the point can be omitted with a diagnostic counter;
- if molecular density is non-negligible while promolecular density is below threshold, the calculation must warn/fail rather than invent weights;
- no arbitrary equal-atom redistribution is allowed.

## 8. Software architecture

### 8.1 Analysis module

Add a focused Hirshfeld analysis module under the existing analysis architecture rather than embedding the method inside CLI/report code.

Responsibilities:

- load/reference the versioned free-atom density library;
- evaluate/interpolate reference densities;
- construct stockholder weights;
- integrate populations;
- compute charges and diagnostics;
- return typed scientific result data independent of presentation.

### 8.2 Services and registry

Expose the analysis through the existing service/result-record system.

The registry entry must include:

- required capabilities;
- deterministic defaults;
- validation status;
- method/version metadata;
- provenance hooks;
- bounded-runtime/resource declaration.

If configurable quadrature options require registry parameter support, add keyword-only parameters without breaking existing callers.

### 8.3 Result schema

The structured result should contain at least:

- method name: `hirshfeld`;
- method definition/version;
- atomic index/element;
- effective nuclear charge used;
- electron population;
- net atomic charge;
- total electrons expected/integrated;
- molecular charge expected/integrated;
- closure residuals;
- quadrature settings;
- reference library identifier/hash;
- density provenance;
- warnings;
- result status;
- scientific validation status.

Do not hide diagnostics merely because the final charge vector appears plausible.

## 9. Public interfaces

### 9.1 CLI

Target form:

`openwfn FILE population hirshfeld`

Optional numerical controls may be exposed only when their semantics are stable and documented. Defaults remain usable without requiring expert tuning.

Human-readable output should present an atomic table plus a compact diagnostic/validation footer.

### 9.2 Python API

Provide a typed API returning the same scientific result represented by the CLI service layer. Avoid a second independent implementation path.

### 9.3 JSON/CSV

JSON must preserve all diagnostics and provenance. CSV may contain the per-atom table plus stable metadata fields or a documented companion metadata record where required.

### 9.4 Batch

Batch analysis is supported only after deterministic defaults and error handling are established. Unsupported inputs are recorded with reasons; they are not silently skipped.

### 9.5 Reports

HTML/Markdown reports gain a Hirshfeld section including the atomic charge table, method definition, validation status, closure metrics, and provenance.

### 9.6 MCP

Read-only MCP exposure is allowed only after CLI/API/batch/report parity tests pass. MCP must return the same registered result and must not introduce separate numerical defaults.

## 10. Validation strategy

### 10.1 Evidence levels

Implementation tests alone do not establish scientific validation.

Evidence is separated into:

1. mathematical/unit tests;
2. numerical invariants and closure tests;
3. grid-convergence tests;
4. independent same-wavefunction reference comparisons;
5. cross-format regression where the underlying density is equivalent;
6. workflow/resource tests.

Only levels 1-3 initially justify Experimental/conditional status. Promotion to Validated requires reviewed independent evidence with documented tolerances.

### 10.2 Molecular validation corpus

Start from the existing everyday-QC corpus and ensure chemically diverse cases for Hirshfeld validation, including at least:

- water;
- methane;
- ammonia;
- carbon dioxide;
- benzene;
- ethanol;
- ammonium cation;
- oxygen triplet;
- diffuse/open-shell OH;
- hydrogen-bonded water dimer.

Add other cases only where they materially test missing elements, polarity, charge state, open-shell behavior, diffuse tails, or basis behavior.

### 10.3 Independent references

Reference charges must come from an independently implemented method/tool operating on the same molecular wavefunction/density where possible.

The reference capture must record:

- tool/software/version;
- input wavefunction hash;
- method settings;
- reference-density convention;
- integration settings;
- reported charges;
- comparison tolerance;
- known convention differences.

Agreement with a tool that uses a materially different free-atom density convention must not be presented as direct numerical equivalence without qualification.

### 10.4 Required failure tests

Tests must cover:

- unsupported element;
- ECP case without validated reference treatment;
- missing molecular density;
- malformed reference data;
- reference-density hash mismatch;
- under-resolved quadrature;
- non-converged tail/spatial extent;
- near-zero promolecular denominator with non-negligible molecular density;
- electron-count mismatch;
- charge-closure failure;
- unrestricted/open-shell input;
- structure-only input;
- batch mixed supported/unsupported inputs.

## 11. Scientific status policy

Initial implementation status: Experimental.

Promotion to Validated requires all of:

- method definition frozen;
- reference-density library provenance complete;
- supported-element scope explicit;
- independent molecular reference comparisons passing documented tolerances;
- convergence studies complete;
- failure behavior tested;
- CLI/API/report/batch parity passing;
- resource checks passing;
- documentation reviewed;
- validation manifest updated with exact evidence boundaries.

A stable package release does not automatically promote the method's scientific status.

## 12. Resource and safety constraints

The implementation must retain openWFN's bounded-resource behavior.

- reject unreasonable grids before allocation;
- evaluate AO and stockholder quantities in chunks;
- avoid constructing molecule-size x full-grid dense tensors when streaming reductions suffice;
- record peak-resource benchmarks for representative small and medium validation molecules;
- ensure batch failure cannot leave corrupt partial outputs presented as complete results.

## 13. Documentation changes

0.11 documentation must include:

- Hirshfeld method page with equations/conventions;
- reference-density provenance page;
- numerical convergence guide;
- limitations/ECP policy;
- validation evidence page update;
- capability map update;
- CLI/Python examples;
- release notes;
- update to ROADMAP wording so existing 0.10.1 validated everyday-QC capabilities are no longer incorrectly described as Experimental.

## 14. Release gates

Before 0.11 stable release:

1. all current 0.10.1 tests remain green;
2. new Hirshfeld unit/integration/failure tests pass;
3. independent reference suite passes;
4. convergence evidence is committed and reproducible;
5. full docs build succeeds with strict checks;
6. security checks pass;
7. browser/workbench tests pass if Hirshfeld is surfaced there;
8. built-wheel verification executes real Hirshfeld workflows from packaged examples;
9. public-package verification repeats the same prescribed installed-package workflow after publication;
10. validation manifest distinguishes runtime success from scientific validation.

## 15. Delivery sequence

Implementation should proceed as separate reviewable units:

1. reference-density data model, provenance schema, generator and normalization tests;
2. reference-density interpolation/evaluation tests;
3. atom-centered quadrature/convergence infrastructure reuse or extension;
4. core Hirshfeld numerical engine with synthetic/invariant tests;
5. molecular real-wavefunction tests and failure semantics;
6. independent reference capture and comparison suite;
7. service/result schema and Python API;
8. CLI/JSON/CSV;
9. batch/report integration;
10. optional MCP/workbench integration after parity tests;
11. documentation/manifest/roadmap/release-evidence updates;
12. full verification and release candidate review.

Each unit must be independently testable. Do not combine unrelated spectroscopy or real-space-analysis work into the same implementation branch.

## 16. Acceptance criteria

The 0.11 Hirshfeld project is complete when a supported wavefunction can be analyzed reproducibly through openWFN and the result includes scientifically defined charges, explicit numerical/conservation diagnostics, versioned reference-density provenance, and matching CLI/Python/batch/report behavior; unsupported cases fail clearly; and any `Validated` label is backed by committed independent evidence rather than package stability alone.

## 17. Future follow-on work

After the Hirshfeld scientific gate is complete, later separately designed projects may consider:

- Hirshfeld-I;
- CM5;
- vibrations/IR/Raman;
- excited states/UV-Vis;
- NTOs;
- analytic density derivatives;
- QTAIM;
- ELF/LOL;
- NCI/RDG;
- basin integration.

These are deliberately excluded from the 0.11 Hirshfeld implementation so the method can be validated thoroughly before openWFN expands further.
