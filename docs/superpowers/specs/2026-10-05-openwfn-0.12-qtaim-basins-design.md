# openWFN 0.12 QTAIM Basin Analysis Design

## Purpose

This project adds Experimental QTAIM atomic-basin population analysis on top of openWFN's existing analytic density, density-gradient, Hessian, QTAIM topology, and deterministic atom-centered quadrature engines.

The scientific goal is to partition the molecular electron density into atomic basins defined by gradient flow and to integrate basin electron populations without substituting a geometric nearest-atom rule or a Becke/Hirshfeld partition for the QTAIM definition.

This work is a separate scientific gate after QTAIM topology, ELF/LOL, and NCI/RDG. It must remain scientifically conservative, bounded in memory and runtime, provenance-aware, and explicit about unresolved trajectories, finite quadrature error, boundary diagnostics, and validation scope.

Public validation status remains `Experimental` after this project unless a later, separate validation review justifies promotion.

## Supported scientific scope

The first implementation supports finite, isolated molecular wavefunctions with a usable real all-electron total electron density.

The initial in-scope contract requires:

- physical nuclei with ordinary all-electron nuclear charges;
- no ghost centers;
- no ECP/pseudopotential centers;
- a finite total-density AO representation that openWFN can evaluate analytically;
- one uniquely matched nuclear attractor basin for every physical nucleus;
- no detected non-nuclear attractor that would capture a finite part of the density in the requested atomic-only result.

Open-shell wavefunctions are allowed when openWFN has a valid total alpha+beta density. The first basin implementation integrates total electron density only. It does not define spin-resolved QTAIM basins.

If the stored density source is SCF density for a calculation that also contains post-HF metadata, the result must identify that density source explicitly. openWFN must not describe an SCF-density basin population as a correlated-density QTAIM charge.

Unsupported ECP, ghost-center, non-nuclear-attractor, ambiguous-attractor, or missing-attractor cases must fail or return an explicitly incomplete/partial result according to the failure mode below. They must never be converted to nearest-nucleus assignments.

## Basin definition

For a scalar electron density `rho(r)`, each basin is the set of points whose density-gradient ascent trajectory terminates at the same attractor.

The numerical flow follows the normalized gradient direction

$$
\frac{d\mathbf r}{ds}=\frac{\nabla\rho(\mathbf r)}{\lvert\nabla\rho(\mathbf r)\rvert}
$$

away from attractor capture regions.

The numerical integrator may use a higher-order predictor/corrector internally, but every accepted step must follow the density-gradient-ascent field and satisfy explicit bounded acceptance rules. There is no nearest-atom fallback.

### Attractor discovery and matching

Atomic-basin integration must not assume that the existing default bounded QTAIM topology search is exhaustive.

For the basin workflow, openWFN must establish the attractor set with a basin-specific deterministic procedure that at minimum seeds from every physical nucleus and may add local deterministic perturbation seeds. Converged `(3,-3)` attractors are merged with documented spatial tolerances.

Each physical nucleus must map uniquely to one nuclear attractor within a documented maximum matching distance. If a nucleus has no unique match, the atomic-basin calculation is not valid.

If the workflow discovers an additional `(3,-3)` non-nuclear attractor that is not uniquely associated with a physical nucleus, the first implementation must reject the atomic-only result rather than silently discard that basin. Support for explicit non-nuclear basins is deferred.

Gaussian basis functions do not reproduce the exact Coulombic nuclear cusp, so the numerical attractor is not required to sit at the exact nuclear coordinate. Matching therefore uses an explicit finite spatial tolerance and reports the attractor-to-nucleus distances.

## Gradient-flow classifier

The classifier accepts arbitrary Cartesian points in bohr and returns, for each point:

- resolved basin index or `null`;
- terminal attractor index when resolved;
- trajectory status/reason;
- accepted step count;
- final position and distance to the captured attractor;
- optional accumulated path length for diagnostics.

Trajectory integration is deterministic and bounded.

Required controls include:

- finite positive nominal step size;
- finite positive attractor capture radius;
- finite positive density-gradient floor;
- maximum accepted path steps;
- maximum backtracks/retries per step;
- finite padded molecular bounds;
- centralized cap on simultaneously evaluated points and total requested quadrature size.

A candidate step must remain finite and inside the allowed bounds. The implementation must require monotonic density ascent up to a documented floating-point tolerance. If a nominal step fails the acceptance rule, the step is reduced by bounded backtracking. Exhausting the retry budget leaves the trajectory unresolved.

A trajectory is unresolved, not guessed, if any of the following occurs before attractor capture:

- nonfinite density or gradient;
- gradient norm below the configured floor away from an attractor;
- exit from the allowed molecular bounds;
- exhausted backtracking;
- maximum step count reached;
- ambiguous simultaneous capture of more than one attractor;
- any other numerical condition that prevents deterministic assignment.

The classifier must support chunked/batched evaluation through the existing analytic density/gradient machinery rather than issuing an unbounded number of one-point AO allocations.

## Population integration

For atom/basin `A`, the electron population is

$$
N_A=\int_{\Omega_A}\rho(\mathbf r)\,d\mathbf r.
$$

For the all-electron first scope, the QTAIM atomic charge is

$$
q_A=Z_A-N_A.
$$

Population integration reuses `iter_atom_centered_chunks` and its deterministic molecular quadrature.

The existing smooth molecular partition weight is used only as an integration quadrature weight that avoids double-counting overlapping atom-centered integration grids. It does **not** define basin membership. Every quadrature point receives its QTAIM basin identity only from the gradient-flow classifier.

For every chunk:

1. obtain quadrature points and integration weights;
2. evaluate total density;
3. classify each point by gradient ascent;
4. accumulate `weight * rho` only into the resolved basin;
5. separately accumulate unresolved quadrature weight and unresolved electron-density contribution.

The calculation must expose both the integrated molecular electron count from the quadrature and the sum of resolved basin populations. It must not force the latter to equal the expected electron count by renormalization.

### Required population diagnostics

Report at minimum:

- per-basin electron population;
- per-atom charge;
- integrated molecular electron count;
- expected electron count for the stored density source;
- molecular electron-count residual;
- sum of resolved basin populations;
- unresolved electron contribution;
- resolved-population closure residual;
- sum of atomic charges;
- expected molecular charge;
- charge closure residual;
- unresolved quadrature weight;
- resolved/unresolved point counts;
- trajectory termination counts by reason;
- active numerical settings and quadrature settings;
- density-source provenance.

A finite but materially nonzero unresolved electron contribution or population-closure error must produce a `partial` result with warnings. It may not be hidden by normalization.

## Basin volume policy

The first implementation does not report a finite isolated-molecule atomic basin volume.

For a finite molecule, exterior atomic basins may extend to infinity. A volume calculated only inside the finite numerical integration region would therefore be a cutoff-dependent box/radial-domain quantity rather than an intrinsic QTAIM atomic volume. Such a quantity must not be presented as an ordinary basin volume.

Any future finite-domain volume diagnostic must be explicitly named as such and belongs to a separate design review.

## Zero-flux boundary diagnostics

QTAIM basin boundaries satisfy the zero-flux condition

$$
\nabla\rho(\mathbf r)\cdot\mathbf n(\mathbf r)=0
$$

for the local boundary normal `n`.

The first implementation will not attempt to construct a publication-quality triangulated basin surface. Instead it will provide a bounded sparse boundary diagnostic independent of the population accumulator.

### Boundary sampling procedure

1. Construct a bounded Cartesian probe grid covering the molecular region at an explicitly configured spacing and padding.
2. Classify probe points with the same gradient-flow classifier.
3. Identify Cartesian neighbor edges whose endpoints resolve to different basins.
4. Bisect each crossing edge by repeated classification until the crossing location reaches a configured spatial tolerance or the bisection limit is exhausted.
5. Group nearby crossing samples locally.
6. Estimate a local surface normal by a deterministic least-squares/PCA plane fit when the local point cloud is sufficiently well conditioned.
7. Evaluate the density gradient at the boundary sample and report the dimensionless residual

$$
\epsilon_{\mathrm{zf}}=\frac{\lvert\nabla\rho\cdot\mathbf n\rvert}{\lvert\nabla\rho\rvert}.
$$

Samples with an ill-conditioned local surface fit, nonfinite gradient, or too-small gradient norm are marked unresolved and excluded from resolved zero-flux statistics. They are counted explicitly.

Report resolved sample count, unresolved sample count, median residual, selected upper percentile (at least p95), and maximum residual. These are diagnostics, not proof that the complete basin boundary has been reconstructed.

The boundary probe has its own centralized point cap and must reject oversized requests before allocating the full probe grid.

## Numerical settings and convergence

Introduce a focused `QTAIMBasinSettings` object containing the gradient-flow and boundary-probe controls and an `AtomQuadratureSettings` value for integration.

Defaults must be deterministic and conservative enough for routine small molecules while remaining bounded for CI and interactive use. Exact numerical defaults are implementation details to be pinned in the implementation plan and tests; changing them after release is a scientific behavior change and requires review.

The validation suite must exercise at least coarse, medium, and fine quadrature settings. A single default-grid result is not sufficient evidence of numerical convergence.

Convergence records must include changes in:

- each atomic population;
- total integrated electron count;
- unresolved electron contribution;
- charge closure;
- zero-flux residual statistics where the boundary diagnostic is enabled.

## Result model and status

Register the read-only named analysis as `qtaim-basins`, with result kind `qtaim_basins`.

The primary payload contains:

- atom indices/elements/nuclear charges;
- matched attractor positions and attractor-to-nucleus distances;
- electron populations;
- QTAIM atomic charges;
- all population/closure diagnostics;
- trajectory diagnostics;
- optional sparse zero-flux diagnostics;
- units;
- formulas and conventions;
- all numerical and quadrature settings;
- density-source/input provenance;
- `validation_status="Experimental"`.

`success` requires all requested basin populations to be resolved with finite values and all predeclared numerical acceptance tolerances to pass.

`partial` is required when the calculation can return meaningful finite populations but one or more declared convergence/closure/zero-flux quality gates fail. Structured warnings must identify which gate failed.

Unsupported scientific cases such as ECP centers, ghost centers, missing/ambiguous nuclear attractors, or detected non-nuclear attractors fail explicitly rather than returning plausible atomic charges.

## Architecture

Create `src/openwfn/analysis/qtaim_basins.py` as a focused module separate from the existing topology engine.

It owns:

- basin settings and diagnostics dataclasses;
- attractor preparation/matching for basin analysis;
- pure gradient-flow trajectory logic;
- batched point classification;
- population accumulation over existing atom-centered quadrature;
- sparse boundary-crossing localization and zero-flux diagnostics;
- ResultRecord adapter.

Reuse rather than duplicate:

- analytic total density and gradient evaluation from the existing real-space engine;
- QTAIM Hessian classification/search primitives where scientifically appropriate;
- `iter_atom_centered_chunks` for molecular quadrature;
- centralized resource-limit definitions;
- existing provenance/capability machinery.

Do not put basin integration into `qtaim.py`; that file remains the topology/critical-point subsystem.

## Public interfaces

### Registry

Register `qtaim-basins` with isolated-molecule, basis, physical-nucleus, and total-density capability requirements.

### Python API

Add a convenience method

```python
calculation.qtaim_basins(...)
```

that uses the same basin engine and provenance contract as the named analysis.

### CLI

Expose the population workflow as

```bash
openwfn FILE population qtaim
```

with bounded optional numerical/convergence controls that map directly to the same settings object.

The CLI must not define different scientific defaults from the Python/registry engine.

### Deferred interfaces

Do not add dedicated basin rendering to Workbench, HTML reports, MCP, or REST in this scientific gate. If the generic analysis registry causes discoverability in an existing read-only interface, it must preserve the same settings, status, warnings, and provenance without introducing an alternate algorithm.

## Unit and integration tests

Required tests include at least:

1. synthetic symmetric two-attractor density with exact symmetry-plane basin boundary;
2. exact half-population integral for that symmetric synthetic density within quadrature tolerance;
3. zero normal density-gradient component on the exact synthetic boundary;
4. deterministic point classification on both sides of the boundary;
5. points exactly/on-near the boundary handled without arbitrary nearest-attractor assignment;
6. monotonic-ascent and backtracking behavior;
7. gradient-floor, out-of-bounds, nonfinite, step-limit, and ambiguous-capture termination reasons;
8. chunked versus unchunked classification equivalence within floating-point tolerance;
9. unique nucleus-attractor matching and ambiguous/missing-match rejection;
10. non-nuclear-attractor rejection for the atomic-only contract;
11. ghost/ECP rejection;
12. population accumulator does not use Becke owner atom as basin identity;
13. unresolved electron contribution is retained and produces partial status;
14. electron-count and charge-closure diagnostics;
15. boundary crossing bisection and local-normal conditioning behavior;
16. boundary probe and quadrature resource rejection before oversized allocation;
17. Python registry/API/CLI parity;
18. JSON-safe output with no NaN/Infinity;
19. density-source provenance preserved for unrestricted and post-HF-containing inputs.

## Independent validation

A merge-quality validation gate requires evidence independent of the openWFN basin algorithm.

The preferred external reference is a version-pinned established QTAIM implementation such as Critic2 operating on the exact same molecular wavefunction files. If Critic2 cannot be used reproducibly for a selected fixture, another established QTAIM implementation may be substituted only with the same provenance requirements. A self-comparison against another openWFN code path is not acceptable independent validation.

The committed reference record must include:

- external program and exact version/commit;
- executable/build provenance where practical;
- exact command/input script;
- input wavefunction SHA-256;
- molecule geometry, charge, multiplicity, electronic method and basis when known;
- external basin-integration settings;
- per-atom populations/charges;
- total population/charge closure diagnostics supplied by the reference program;
- generation date and any parser/conversion steps;
- redistribution/license status of all committed fixtures.

Initial named molecular reference set should contain at least:

- water;
- methane or another simple C/H molecule;
- ammonia or another simple N/H molecule;
- one less-symmetric polyatomic all-electron molecule if a redistribution-safe wavefunction fixture is available.

Reference molecules must avoid known non-nuclear attractors and ECPs for this first scope.

For every named case, compare coarse/medium/fine openWFN quadratures and require predeclared tolerances for:

- per-atom electron populations;
- per-atom charges;
- total electron-count closure;
- total charge closure;
- unresolved electron contribution.

Zero-flux diagnostics are validated independently with the exact synthetic field and numerically on real molecules; an external program need not expose identical surface residual statistics for the population comparison to remain useful.

If reproducible external basin-population evidence cannot be obtained, the PR is scientifically blocked from merge rather than relabeled as validated by internal tests alone.

Passing the external reference gate validates only the named all-electron molecular cases and settings. It does not justify a universal QTAIM basin claim.

The feature may be marked ready to merge only when all of the following hold on the exact PR head:

- implementation follows this scientific contract;
- required synthetic tests pass;
- coarse/medium/fine convergence tests pass for the declared named cases;
- independent external QTAIM population references are committed with complete provenance and pass predeclared tolerances;
- Python/CLI/registry parity tests pass;
- resource-safety tests pass;
- documentation and validation-status records are synchronized;
- the full supported Python/platform matrix, lint, security, packaging, scientific validation, and browser regression workflows are green;
- whole-branch review finds no unresolved scientific or interface contract gaps.

Even after this merge gate passes, the public basin method remains `Experimental`.
