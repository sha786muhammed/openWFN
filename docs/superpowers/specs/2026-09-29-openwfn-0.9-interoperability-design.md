# openWFN 0.9 Interoperability Design

Date: 2026-09-29

## Purpose

openWFN 0.9 will make interoperability a first-class product capability without weakening scientific correctness or breaking the existing Gaussian FCHK workflow.

The release goal is:

> Many scientific file formats -> one stable openWFN data contract -> explicit capability-aware analysis.

The release will use IOData as an optional interoperability backend. IOData is a parser/translation layer only; openWFN remains authoritative for the public API, canonical data model, analysis behavior, provenance, validation status, and result contracts.

The 0.9 release target is **Stable ingestion support for every IOData-readable input format exposed by the pinned IOData version**. A format reaches Stable only after its automated openWFN format contract passes. If a backend format cannot meet that contract, 0.9 release scope must be revised explicitly; the project must not silently advertise it as Stable.

## Product principles

1. Preserve current FCHK behavior unless a separately justified bug fix requires a change.
2. Keep IOData optional; core FCHK users must not be forced to install it.
3. Never infer analysis support from a filename alone.
4. Never claim an analysis is supported unless the normalized data actually satisfies that analysis's requirements.
5. Never expose raw IOData objects as part of openWFN's public API.
6. Every stable format claim requires automated fixture-backed validation.
7. Missing or ambiguous data must produce explicit unsupported/partial behavior, warnings, or provenance rather than silent substitution.
8. 0.9 is an interoperability release, not a broad scientific-method expansion.

## Scope

### In scope

- A new top-level canonical container that can represent molecular wavefunctions, structures, periodic data, volumetric data, and other imported scientific payloads without forcing them into the current molecular-only shape.
- A capability engine shared by CLI, Python API, batch, and analysis dispatch.
- IOData-backed ingestion for the full IOData-readable input-format surface available in the pinned interoperability dependency version.
- Stable input support defined by deterministic ingestion, provenance, normalized representation, capability reporting, clean unavailable-analysis behavior, and automated validation for every format in the release matrix.
- Mixed-format batch processing.
- Cross-format validation for equivalent molecular wavefunction formats where meaningful.
- User-facing documentation and a generated format/capability matrix.
- Backward-compatibility tests for current FCHK workflows.

### Explicitly out of scope

- QTAIM or other major new wavefunction-analysis families.
- A plugin ecosystem.
- LLM or AI features.
- New ML models.
- A GUI rewrite.
- Attempting to reproduce Multiwfn feature breadth.
- Treating every readable format as if it contains all molecular-wavefunction information.

## Stable support definition

"Stable format support" in 0.9 means:

- the file format is accepted through a documented ingestion path;
- the source is represented in openWFN's canonical container without inventing unavailable scientific data;
- source checksum, parser/backend identity, backend version, source format, transformations, omissions, and warnings are preserved;
- the capability engine deterministically reports which data and analyses are available, derived, missing, or unsupported;
- unsupported analyses fail as structured scientific results rather than unexplained crashes;
- the format has redistribution-safe fixture coverage and an automated format-contract test.

Stable format support does **not** mean that every openWFN analysis works for every format. A structure-only format, a volumetric-grid format, a periodic structure format, an integral format, and a molecular-wavefunction format expose different scientifically valid capability sets.

## Architecture

### Current foundation

The existing `CalculationData` remains the canonical molecular-wavefunction object consumed by current analyses. It is not removed or silently repurposed.

A new top-level container named `OpenWFNData` will represent heterogeneous scientific inputs while preserving typed boundaries.

Initial conceptual structure:

```text
OpenWFNData
├── calculation: CalculationData | None
├── structure: StructureData | None
├── periodic: PeriodicData | None
├── grids: tuple[GridData, ...]
├── integrals: IntegralData | None
├── metadata: SourceMetadata
├── provenance: Provenance
└── capabilities: CapabilitySet
```

Implementation may split a component into smaller typed objects if required for scientific correctness, but formats must map into openWFN-owned types rather than raw IOData objects.

### Data flow

```text
Native openWFN parsers --------------------┐
                                          │
IOData-readable source -> IOData adapter --┼-> OpenWFNData
                                          │
                                          v
                                  Capability engine
                                          │
                   ┌──────────────────────┼──────────────────────┐
                   v                      v                      v
                 CLI                  Python API               Batch
                                          │
                                          v
                                  openWFN analyses
```

### Native parsers remain authoritative where already established

Existing openWFN native parsers, especially Gaussian FCHK, remain the preferred path for formats where openWFN already has a validated implementation. IOData does not replace a stronger native parser merely for architectural uniformity.

The parser registry will decide between native parsing and IOData-backed adaptation according to explicit registration, not heuristics scattered across the codebase.

## IOData adapter boundary

A dedicated adapter module will isolate IOData from the rest of openWFN. The adapter has four responsibilities:

1. Load a supported source through IOData.
2. Normalize compatible fields into openWFN-owned typed objects.
3. Record conversions, omissions, assumptions, ambiguities, and backend metadata.
4. Return an `OpenWFNData` object.

Raw IOData objects must not leak into:

- public Python return types;
- analysis function signatures;
- result schemas;
- CLI output contracts;
- batch manifests.

This keeps openWFN independent from IOData's internal API and allows the backend to be upgraded or replaced later without breaking users.

### Optional dependency

IOData will be installed through an interoperability extra:

```bash
pip install "openwfn[interop]"
```

Core installation remains:

```bash
pip install openwfn
```

If a user opens an IOData-backed format without the interoperability extra installed, openWFN must return a concise actionable message naming the required extra. It must not expose a raw `ImportError` stack trace for expected missing-optional-dependency behavior.

## Provenance contract

Imported data must preserve enough information to reproduce and audit the conversion path.

The provenance record should include, where available:

- source path;
- source SHA-256;
- source format;
- source program and version;
- openWFN parser/adapter identity and version;
- IOData backend version recorded at runtime;
- unit conversions;
- orbital/basis ordering transformations;
- occupation normalization;
- omitted source fields that openWFN does not yet model;
- ambiguity warnings;
- derivations performed by openWFN.

Example conceptual payload:

```json
{
  "source_format": "molden",
  "parser": "openwfn-iodata-adapter",
  "parser_version": "1",
  "backend": "iodata",
  "backend_version": "recorded-at-runtime",
  "transformations": [
    "coordinates converted bohr -> angstrom",
    "orbital occupations normalized to openWFN convention"
  ],
  "warnings": []
}
```

If IOData exposes data that openWFN cannot represent safely, openWFN must preserve the fact that information was omitted in provenance and mark dependent capabilities unavailable. It must not silently discard scientifically relevant information while reporting full support.

## Capability engine

### Requirement declarations

Every registered analysis will declare its data requirements. The existing `AnalysisDefinition` will be extended with a typed requirement set.

Conceptual example:

```python
AnalysisDefinition(
    name="mulliken",
    version="2",
    result_kind="mulliken_population",
    requires={
        "molecule",
        "basis",
        "density_or_orbitals",
        "ao_overlap",
    },
    runner=...,
)
```

Capabilities are determined from normalized data after parsing. Filename suffixes may select a parser, but they must never decide scientific capability.

### Capability vocabulary

The initial capability vocabulary must cover at least:

- structure;
- molecular metadata;
- periodic cell;
- basis;
- alpha orbitals;
- beta orbitals;
- orbital occupations;
- total density matrix;
- spin density matrix;
- derivable total density;
- AO overlap;
- volumetric grid;
- electronic energy;
- integral data.

Implementation may split these into finer capabilities where scientifically necessary.

### Capability states

The engine will distinguish at least:

- `available`: present directly in normalized input;
- `derived`: reproducibly derivable from available data;
- `missing`: not supplied and not derivable;
- `unsupported`: openWFN currently has no safe representation or implementation.

### Analysis dispatch

Before running an analysis:

1. Resolve the analysis definition.
2. Evaluate declared requirements against `OpenWFNData`.
3. If satisfied, unwrap/pass the relevant typed component to the analysis runner.
4. If not satisfied, return a structured unavailable/unsupported result identifying the missing requirements.

Expected scientific unavailability must not become a generic exception or batch crash.

## Public API

`openwfn.load()` remains the primary Python entry point.

Examples:

```python
import openwfn

calc = openwfn.load("molecule.fchk")
calc.summary()
calc.frontier()
```

The same user-facing API will work for other formats when the capability requirements are satisfied:

```python
calc = openwfn.load("molecule.molden")
calc.summary()
calc.frontier()
calc.capabilities()
```

Advanced users may inspect the normalized canonical container through `calc.data`, which will return `OpenWFNData`.

Backward-compatibility rule:

> Existing supported FCHK analyses and result semantics must remain compatible in 0.9 unless a separately justified scientific bug fix requires a change.

Any intentional result-schema evolution must use explicit schema/version migration rather than silent field reinterpretation.

## CLI

Existing commands continue to work:

```bash
openwfn molecule.fchk summary
openwfn molecule.fchk orbitals frontier
```

Equivalent commands should work for other inputs when capabilities allow:

```bash
openwfn molecule.molden summary
openwfn molecule.wfx orbitals frontier
openwfn calculation.out summary
```

### New capability command

Add a user-facing capability command:

```bash
openwfn FILE capabilities
```

Expected output categories:

- detected source format;
- parser/backend;
- stable support status;
- available/derived/missing/unsupported data capabilities;
- available/unavailable analyses;
- reason for each unavailable analysis where useful.

Example:

```text
Input: molecule.molden
Format: Molden
Backend: IOData
Status: Stable

Data
  ✓ structure
  ✓ basis
  ✓ alpha orbitals
  ~ total density: derivable
  ✗ spin density

Analyses
  ✓ summary
  ✓ frontier
  ✓ density
  ✗ beta-frontier — beta orbitals unavailable
```

## Batch behavior

Batch processing becomes format-agnostic.

A directory may contain mixed inputs such as:

```text
water.fchk
benzene.molden
oxygen.wfx
orca_job.out
structure.xyz
```

The same requested analysis list is evaluated independently for each input according to capabilities.

One unsupported analysis for one file must not crash the whole batch. The batch manifest should record structured unsupported/partial/failure states for each file-analysis pair.

Existing resume/checksum semantics should be preserved.

## Format coverage strategy

The interoperability adapter will expose the full IOData-readable input-format surface available in the pinned IOData version, including molecular, structural, periodic, grid, and integral formats.

Examples expected in the matrix include formats such as:

- Gaussian FCHK/log/input;
- Molden;
- WFN;
- WFX;
- MWFN;
- ORCA log;
- Q-Chem log;
- GAMESS;
- CP2K;
- QCSchema JSON;
- cube;
- PDB;
- SDF/MOL2/XYZ/ExtXYZ;
- VASP POSCAR/CHGCAR/LOCPOT;
- GROMACS/CHARMM structure-related formats;
- FCIDUMP;
- Molekel;
- every other IOData-readable input format exposed by the pinned backend version.

The exact release matrix must be generated from the pinned backend plus openWFN's fixture registry so documentation cannot drift from implementation.

## Periodic, grid-only, and integral inputs

The current `CalculationData` foundation is molecular and isolated-system oriented. Therefore periodic, grid-only, and integral-only sources must not be forced into fake molecular-wavefunction objects.

### Periodic data

Periodic cell vectors and boundary conditions require a dedicated typed representation in the top-level container. Molecular analyses that assume isolated boundary conditions must declare that requirement and be unavailable for periodic data unless explicitly generalized and validated.

### Volumetric data

Grid-only inputs should populate volumetric components and enable only analyses that depend on volumetric data and associated structure metadata.

### Integral data

Integral-only representations such as FCIDUMP should populate an integral component and capability metadata. They should not fabricate orbital or density capabilities.

## Validation strategy

### Stable-format contract

Every format labeled Stable must satisfy an automated contract covering:

1. successful parsing;
2. source checksum and provenance preservation;
3. unit normalization;
4. expected canonical components;
5. expected capability map;
6. successful execution of every analysis expected to be available;
7. clean structured rejection of unavailable analyses;
8. reference or round-trip checks where scientifically meaningful.

A format is not Stable merely because IOData can parse it.

### Fixture policy

Every stable format needs at least one redistribution-safe fixture with documented provenance. Where format behavior varies substantially by program/version or optional sections, multiple fixtures are required.

Pending formats are not counted as passes.

### Cross-format equivalence

For FCHK, Molden, WFN, WFX, and other wavefunction formats where equivalent scientific content can be exported from the same calculation, the validation suite should compare representations of the same underlying calculation.

Checks should include, where present and meaningful:

- atom identities and coordinates;
- charge and multiplicity;
- electron count;
- basis size/order information;
- MO energies;
- occupations;
- density reconstruction/integration;
- supported population analysis;
- frontier-orbital results;
- provenance and transformation records.

Tolerances must be documented per metric. The suite must not demand equality for properties a target format cannot represent.

### Program-specific formats

For ORCA, Q-Chem, GAMESS, CP2K, and other program outputs, validation should use representative redistribution-safe fixtures and compare parsed/normalized values with independently established references where available.

### CI

The 0.9 release gate should include:

- unit tests;
- parser/adapter tests;
- capability-engine tests;
- format-contract tests;
- cross-format scientific regressions;
- existing FCHK scientific validation;
- mixed-format batch tests;
- Linux/macOS/Windows CI;
- supported Python-version matrix;
- docs build;
- wheel/install smoke tests for both core and `[interop]` installations.

## Error behavior

Expected error classes and outcomes:

| Condition | User-facing behavior |
|---|---|
| unsupported/unrecognized format | concise parse error naming the format |
| IOData-backed format but `[interop]` is missing | actionable install instruction |
| file loads but required scientific data is absent | structured unsupported analysis with missing requirements |
| conversion ambiguity | provenance warning; capability may be withheld |
| scientific conservation/validation failure | partial/failed result; never silent success |
| malformed external file | parse failure scoped to that input |
| one bad file in batch | record failure for that file; continue other files unless configured otherwise |

## Documentation

0.9 documentation should add:

- an interoperability overview;
- installation instructions for `[interop]`;
- a generated format matrix;
- capability semantics;
- examples using FCHK, Molden, WFN/WFX, and at least one program-output format;
- mixed-format batch examples;
- provenance examples;
- limitations for periodic, grid-only, and integral inputs;
- validation methodology and tolerances;
- backward-compatibility/migration notes.

The format matrix must be generated or test-checked against the format-contract registry so docs cannot advertise unsupported formats accidentally.

## Implementation phases

### Phase 1 — Foundation

- Add `OpenWFNData` and supporting typed components.
- Add capability declarations and capability evaluation.
- Add `capabilities` command/API.
- Preserve existing FCHK behavior and tests.

### Phase 2 — IOData interoperability

- Add `[interop]` optional dependency.
- Add IOData adapter boundary.
- Normalize provenance and transformations.
- Register the full pinned IOData-readable input-format surface.

### Phase 3 — Stable-format validation

- Add redistribution-safe fixtures for every format in the 0.9 release matrix.
- Add format-contract registry/tests.
- Add cross-format equivalence cases.
- Add program-specific reference checks.
- Generate/test the public format matrix.

### Phase 4 — Public integration

- Route CLI, Python API, and batch through the same capability engine.
- Add mixed-format batch behavior.
- Finish docs and migration notes.
- Run full cross-platform, packaging, and scientific release validation.

## Release acceptance criteria

openWFN 0.9 is ready only when all of the following are true:

- Existing FCHK workflows pass backward-compatibility tests.
- Core installation works without IOData.
- `[interop]` installation works across supported Python/platform CI.
- Every IOData-readable input format exposed by the pinned backend and advertised for 0.9 has fixture-backed Stable contract coverage.
- No format is advertised as Stable solely because IOData recognizes it.
- Capability decisions are shared by CLI, Python, and batch.
- Unsupported analyses return structured reasons instead of generic crashes.
- Provenance includes backend identity/version and documented transformations.
- Mixed-format batch runs are deterministic and resumable.
- Cross-format equivalence tests pass within documented tolerances where meaningful.
- Public documentation matches the tested format registry.
- No raw IOData object is exposed in the public API or result schemas.

## Future work after 0.9

After the interoperability foundation is stable, later releases may consider:

- native parsers where they materially improve fidelity;
- plugin architecture;
- deeper periodic analysis;
- QTAIM/topology integrations;
- excited-state integrations;
- ML-ready descriptors and workflow integrations;
- remote service layers.

These are intentionally not part of 0.9.
