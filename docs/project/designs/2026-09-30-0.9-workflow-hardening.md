# 0.9 workflow hardening design

## Purpose and scope

Before broad scientific validation, make the existing 0.9 development code dependable for a person bringing one file or a large, mixed collection of real files. A researcher should be able to inspect each file, run every analysis its data actually supports, and receive an understandable outcome for every input. One unsupported or damaged file must not silently disappear, corrupt another result, or make a batch appear wholly successful. Ghost and ECP center identity must not disappear during normalization or an export without notice.

This design addresses seven confirmed workflow gaps in the CLI, Python API, and shared core. It does not add new scientific analysis methods, claim that every possible file variant or every analysis is supported, or change the published 0.8.2 package. Existing FCHK numerical behavior and result schema 1.0 remain compatible. Future REST and MCP interfaces should call the same core operations and consume the same result envelopes; neither interface is part of this pass.

The user-facing promise is **no silent loss**: each discovered file is identified as analyzed, partially analyzed, unsupported, or failed, with a reason and source checksum when readable. “Without error” means predictable behavior and actionable diagnostics for files openWFN cannot interpret; it cannot mean scientifically valid answers from absent wavefunction data or unknown formats.

## Input routing and inspection

`load(path, *, format_hint=None)` exposes the existing canonical loader's format hint through the public Python API. The CLI accepts `--input-format FORMAT_ID` for a single input or a homogeneous batch. A mixed batch may provide a JSON format map whose keys are input paths and values are registered format IDs; paths are resolved relative to the map file. An invalid ID, a map entry for a missing file, or conflicting hints is rejected before analysis starts. The manifest records the effective format for each input.

Ordinary filenames continue to route automatically. Detection and batch discovery recognize common CHGCAR, LOCPOT, and POSCAR filename prefixes, including the repository's suffixed fixtures, without treating arbitrary text as a quantum-chemistry file. Ambiguous `.json`, `.dat`, and program-output fixture names need an explicit hint or format-map entry. Discovery must list unsupported inputs; it must not silently omit a file whose format was explicitly declared.

`doctor` and `capabilities` use the same canonical loader. `doctor` keeps its existing native-file fields where possible and adds the canonical component/analysis report for interoperability files. A failed parse is reported as a failure, not as a file with missing capabilities.

## Center identity and structure summaries

The normalized structure retains an optional effective nuclear charge for each center, independently of atomic number. The field is length-checked, finite, non-negative, and preserved from IOData `atcorenums` and native molecules. A zero effective charge identifies a ghost center; a lower positive effective charge can represent an ECP center. Missing charges remain unknown rather than being guessed from atomic number.

The registered `summary` analysis keeps its current full-calculation result. When only a valid structure exists, it instead returns a **partial** structure summary with center count, known physical-nucleus and ghost counts, available charge/multiplicity, and explicit unavailable fields. It does not calculate an electron count, frontier orbital, population, or molecular energy from geometry. Unknown effective charges must not be classified as ghosts or physical nuclei without qualification. Periodic structures are labeled periodic and do not acquire isolated-molecule capability. The high-level geometry summary follows the same center-count convention.

XYZ, PDB, MOL, and SDF cannot faithfully encode effective nuclear charges. A structure export containing a ghost or ECP center therefore succeeds only with an explicit loss warning in its `ResultRecord` and human-readable output; the warning identifies the information lost. The direct Python writer returns or emits the same warning. Cube output continues to preserve effective nuclear charges in its header. Existing non-ghost, non-ECP exports are unchanged.

## CLI result and batch contract

For `--format json`, every completed command writes exactly one valid result envelope to stdout. Runtime, input, and analysis failures use a failed envelope with a nonzero exit code. Legacy `info`, `bonds`, `graph`, `view`, and `xyz` commands use the same renderer instead of printing colored text. `--quiet` suppresses progress and incidental text, not the final JSON envelope. Help and shell-level argument usage remain text, including malformed command-line syntax before a command can run.

Batch processing still isolates per-file failures and writes its manifest and CSV index. The top-level result is `success` with exit 0 only when all input records succeed; `partial` with exit 0 when there are partial records but no errors; and `failed` with a nonzero exit code when any record errors. In `--fail-fast` mode, the manifest states that processing stopped early and lists the inputs actually attempted. The batch result and manifest report unsupported discovered files separately from parse/analysis errors. A script requiring every requested analysis can test for `status == "success"`; a script requiring only no hard failures can use the exit code.

For a directory input, the manifest also accounts for files rejected during discovery. Unsupported files retain their paths and reasons; they are not counted as successful analyses. Their presence makes the top-level batch `failed` with a nonzero exit code, even if all accepted files succeeded; an all-unsupported directory still produces a manifest. Per-file records retain successful analyses when another requested analysis is unavailable, so one missing capability does not discard usable results.

Batch resume fingerprints include the openWFN version, a maintained implementation token for unreleased source changes, relevant schema and analysis versions, the optional interoperability backend version, requested analyses, spin selection, and effective format hints. Existing cached records with old fingerprints are recomputed. Input checksums remain part of per-file cache validation. Each batch manifest records the software and backend versions used.

## Verification and boundaries

Tests must first reproduce each observed failure. They cover the 25 fixture names through public CLI/API paths, explicit hints and a mixed format map, a real upstream QCSchema ghost sample, native ghost/ECP fixtures, structure-only and periodic summaries, lossy exports, JSON success and failure output, mixed batch exit codes, unsupported and all-unsupported directories, cache invalidation, resume, Unicode/spaced paths, and malformed files. The existing 514-test suite, interoperability fixture validation, pinned external benchmarks, and representative real mixed-file batch are rerun after changes.

These tests are workflow evidence, not independent scientific validation. Real ghost/ECP wavefunctions, broader charged/open-shell systems, larger molecules, Linux execution, and independently generated non-Gaussian numerical references remain the next validation phase. No publication, tag, or package-index upload is part of this hardening pass.
